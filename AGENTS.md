# turbine — Notes for AI Agents

Turbine is a distributed task queue with swappable storage back ends: the core [queue](queue/) package plus the [queue_mongo](queue_mongo/) (production, distributed) and [queue_filesystem](queue_filesystem/) (single-worker, development) storage providers. Start with the [README](README.md) and the per-package READMEs — they carry the operational detail; this file holds the contracts and foot-guns that cut across them.

## Delivery and consumer contracts

- **Delivery is at-least-once on the mongo backend — consumers must be idempotent.** Locking is timeout-based, not transactional: a worker that dies after executing a task but before `DeleteTask` leaves the record in place, and it becomes claimable again once its `timeoutDate` passes. Retries via `queue.Error` re-run the task too. Never write a consumer that breaks when its task runs twice.
- **The filesystem backend and Inline tasks are at-most-once, by design.** `queue_filesystem.GetTasks` deletes the spool file before the task runs, and `WithInline` tasks are never stored or retried — a crash mid-task loses them. Don't "fix" either into at-least-once; pick the mongo backend when redelivery matters.
- **`Error` means retryable, `Failure` means permanent.** `queue.Error(err)` re-queues with exponential backoff (`2^RetryCount` minutes) until `RetryCount` reaches `RetryMax`, then becomes a failure; `queue.Failure(err)` goes straight to the error log and the task is deleted. **Only a failure is reported through `derp.Report`**: an explicit `Failure`, or an `Error` whose retries have run out, is reported exactly once, from `onTaskFailure`. A retry is logged at debug level and never reported, so a consumer can return `Error` for a transient fault without flooding the error log. Before this, every retry was reported, and a memory-only queue reported each `Failure` twice. `queue.Requeue(delay)` marks THIS run successful and publishes a fresh copy (identity and counters reset) to run again. `queue.Ignored()` means "not my task" and passes it to the next registered consumer, so every consumer must ignore names it doesn't own. Any other status is converted to an immediate `Failure` by `dispatch` — that backstop is deliberate so a new status can never silently pass as success.
- **`Consumer` requires all five methods, and that is the point.** `Run` does the work; `OnSuccess`, `OnError` and `OnFailure` are how the queue reports what it decided. Optional hooks discovered by type assertion would fail silently the moment a name or signature drifted, so they are mandatory and a consumer with nothing to say returns `nil`. Only the consumer whose `Run` handled the task is notified, and a hook's own error is reported and discarded — a hook cannot change what the queue has already decided. Do NOT export an embeddable no-op base: embedding it lets a typo'd hook fall through to the no-op, which is the failure the required methods prevent. The test-only `consumerFunc` in [consumer_test.go](queue/consumer_test.go) is that base, and it stays unexported for this reason.
- **Every publish-time rule lives in `prepareTask`, and `Publish` and `Schedule` both call it.** It runs the `PreProcessor`, then each Consumer's `OnPublish`, then fills in the defaults for anything still unset — in that order, so a hook can tell "unset" (`-1`) from "deliberately set to the default". `Schedule` used to skip all of it, which stored `NewTask`'s sentinels verbatim: a `RetryMax` of `-1` makes `onTaskError` compute `0 >= -1` and abandon the task on its very FIRST failure, and a `Priority` of `-1` sorts ahead of everything because lower runs first. Any new entry point onto the queue routes through `prepareTask` or inherits that bug.
- **`OnPublish` fires again on a requeue, because a requeue is a new publish.** `requeueTask` re-enters `Publish` with a fresh identity, so the copy that runs next earns a fresh pass through the publish-time rules — same as the `PreProcessor` always has. A hook that must fire only once per logical task needs its own guard; `TestConsumerHooks_Requeue` pins the sequence.
- **A panicking Consumer must never reach the worker goroutine.** `consumeSafely` wraps every pooled run: it recovers, reports, and then routes the task through `onTaskError` so it backs off and is eventually abandoned. Dropping it instead would leave the storage record in place, to be re-locked and re-panicked every time its lease expired. `runInline` recovers too but does NOT route to `onTaskError`, because an Inline task is at-most-once and was never stored.
- **A panicking task is recorded but announced to nobody, and that is a known gap.** The panic unwinds out of `dispatch`, losing the value that named which Consumer was handling the task, so `consumeSafely` passes a nil `Consumer` and the outcome hooks are skipped — a consumer that panics is retried and eventually abandoned in silence. `onTaskError` and `onTaskFailure` therefore guard on `consumer != nil`, which is the ONLY reason that guard exists; `onTaskSuccess` needs none, because a panic never reaches it. The fix is to recover inside `dispatch` around `consumer.Run`, turning a panic into a normal `Error` result with the consumer still in hand; `TestConsumeSafely_PanicNotifiesNobody` pins today's behavior and should fail when someone does it.
- **An outcome hook is handed the Task as it stood when that attempt ran.** `onTaskError` builds the next attempt as a separate value (`retry`) for this reason: mutating `task` in place would give the hook a `RetryCount` that already counts this failure, so a Consumer calling `IsFinalAttempt()` inside `OnError` would get the answer for the NEXT run. `onTaskFailure` copies for the same reason. `TestConsumerHooks_HookSeesTheAttemptThatRan` pins it at the 7-of-8 boundary, where the two answers differ.
- **The handler that records an outcome is the handler that announces it.** `onTaskSuccess`, `onTaskError` and `onTaskFailure` each take the handling `Consumer` and fire their own hook, after the queue has written the outcome — so a hook that reads storage always sees the recorded state. `consume` used to call the hooks itself, which meant re-deriving the retry-vs-abandon decision with `Task.IsFinalAttempt()` alongside the real `RetryCount >= RetryMax` guard inside `onTaskError`. Two copies of one decision, in two files. Do not move a hook call back out to the caller; the guard in `onTaskError` is now the only place that decides, and its abandon path delegates to `onTaskFailure`, which is the only place that announces a failure.
- **`runInline` calls its own hooks, and that is correct.** It is the only caller left that does, because an Inline task is never stored — there is no outcome to record, so there is no handler to own the announcement. Do not "fix" it to match the pooled path.
- **`OnFailure`, not `OnError`, is called when a retry-able error has no retries left**, because `OnError` would promise a run that never happens. `IsFinalAttempt` now has no caller inside the queue — it survives as a read-only helper for consumer code, and `TestTask_IsFinalAttempt_MatchesTheQueue` checks it against the real queue at every retry count rather than restating the arithmetic. An Inline task is at-most-once, so `runInline` reports any failure as `OnFailure` for the same reason.
- **`IsFinalAttempt` is `RetryCount >= RetryMax`, never `RetryMax-1`.** `RetryCount` counts attempts that have already FAILED, so with the default `RetryMax` of 8 a task runs nine times and the ninth (RetryCount 8) is the one abandoned. Measured, not derived: RetryCount 7 of 8 is still retried. The off-by-one version reports "giving up" a whole attempt early and then runs again anyway.
- **Task argument keys are a persisted wire format.** Arguments are written to storage as-is and drain over hours or days, so renaming a key strands already-queued tasks. A consumer renaming an argument must read the new key with a fallback to the old one until the persistent queue has fully drained; only then may the fallback be removed. Argument values must round-trip through BSON/JSON (`mapof.Any`) — plain data only, never closures or live pointers.

## Publish and shutdown

- **`Publish` runs the `PreProcessor` once, then routes the task itself.** `requeueTask` re-enters `Publish` on purpose: a requeued task gets a fresh identity, so it is a new publish and earns a fresh pre-processing pass.
- **There is no in-memory delay, and there must not be one again.** `WithAsyncDelay` — a timer goroutine that re-published the task after N milliseconds — was removed on 2026-09-17. Its only consumer was one Emissary call site, where a one-second sleep let a request transaction commit before a priority-16 task ran immediately and tried to load the row; that race is what Emissary's `tools/postcommit` now closes properly, so the sleep had been dead weight since 2026-07-13. A delay worth having is a durable one: `Schedule` and `WithDelaySeconds` write a future `StartDate` to the storage provider and survive a restart.
- **Every process-local goroutine registers with `q.workers` before launch, and every `q.buffer` send selects on `q.done`.** Workers and inline runners both follow this pattern ([queue-worker.go](queue/queue-worker.go), [queue-inline.go](queue/queue-inline.go)). A bare `q.buffer <- task` deadlocks against `Stop` when the buffer is full, and an untracked goroutine outlives shutdown. `Stop` is idempotent via `sync.Once`; publishing an Inline task after `Stop` errors fast, while storage-backed publishes still write (another process or the next restart picks them up — that asymmetry is intentional).
- **The `backoff` exponent is clamped at BOTH ends.** `2^28` minutes overflows `time.Duration` to a negative value, which schedules the retry in the past and hot-loops the queue — so the upper clamp of 27 stays, even though no real retry policy reaches it. The lower clamp is newer and load-bearing in a different way: `backoff` shifts (`1 << exponent`) rather than calling `math.Pow`, and in Go a variable shift by a NEGATIVE amount is a run-time panic. A corrupt or hand-edited record with a negative `RetryCount` would crash a worker, so it is treated as the first attempt.

## Allocation

- **The `consume` path allocates nothing, and [alloc_bench_test.go](queue/alloc_bench_test.go) keeps it that way.** `BenchmarkConsume_Success` reports 0 allocs/op. The only per-task allocations in the package are the `Task` itself inside `NewTask` and `Publish`, and both are forced by taking `*Task` — in `TaskOption` and in `Consumer.OnPublish`. Neither can be removed without changing those signatures, and a 144-byte `Task` is noise beside the database write the task is about to do. Do not trade the API for it.
- **`queue_mongo` sizes its result slices to `lockQuantity`, which is load-bearing.** `GetTasks` and `pickTasks` both know their batch is capped at `lockQuantity`, so `make([]T, 0, lockQuantity)` lets the driver's cursor fill them without regrowing. Measured over a 16-task batch, dropping the capacity costs 7752 B and 38 allocs instead of 5400 B and 34, because every doubling copies 144-byte `Task` values.
- **`Task` is 144 bytes and its field order is already tight.** Every field is 8-byte aligned, so reordering saves nothing; only the trailing `Inline bool` pads, and it would pad in any arrangement.

## Signatures and priority

- **`queue_mongo.isDuplicateSignature` must exclude the task's own `_id`.** `SaveTask` is also how a retry writes its updated counters back; if the duplicate check matches the task's own record, the write-back is silently discarded, `RetryCount` never advances, and the task re-runs every `timeoutMinutes` forever. The `$ne: taskID` filter is the fix — never remove it.
- **Signature duplicates are dropped silently, and a signed task never runs immediately.** `SaveTask` returns `nil` without writing when another task holds the signature (callers cannot tell "saved" from "skipped"), `allowImmediate` refuses signed tasks so the dedup check always sees storage, and `WithSignature` + `WithInline` is rejected at publish (nothing stored to dedup against). `Queue.Delete(signature)` requires a storage provider and is unimplemented on the filesystem backend.
- **Lower priority numbers run first, and both mongo sorts must stay identical.** `pickTasks` and `GetTasks` each sort priority-ascending then `startDate`; if they diverge, a locked batch dispatches out of priority order. Tasks with priority ≤ `runImmediatePriority` (default 16) skip storage into the in-memory buffer when there is room.

## Deliberate non-fixes

- **`Option` vs `QueueOption` naming stays as-is** — reviewed and ruled not a problem.
- **`queue_filesystem.SaveTask` always mints a new `TaskID`** — reviewed and ruled not a problem; a retry write-back becomes a new spool file.
- **`queue_filesystem.DeleteTask` treats a missing file as success** — `GetTasks` already removed the spool file when it handed the task to a worker, so the completion-path delete always finds it gone.
- **A memory-only queue retries with no backoff delay** — with no storage, `onTaskError` puts the task straight back on the buffer. Retry delays and future scheduling require a storage provider.

## Known issues, deferred

- **The storage poller is not registered with `q.workers`** (LOW priority, MEDIUM effort). `Start` launches `go q.start()` without `workers.Add(1)`, so `Stop` returns while the poller may still be inside its one-minute `time.Sleep`; it exits at the top of the next loop. That contradicts the "every process-local goroutine registers with `q.workers`" rule above, and it is currently deliberate — registering it would make `Stop` block for up to a full minute. The real fix is to make the wait interruptible (`select` on `time.After` and `q.done`), after which the poller can be both tracked and prompt.
- **`Storage` carries no `context.Context`** (LOW priority, MEDIUM effort). All four methods are context-free, so `Stop` cannot cancel an in-flight query; `queue_mongo` roots its own timeouts at `context.Background()` in [utils.go](queue_mongo/utils.go). Fixing it means a context parameter on every `Storage` method and both providers, and the parameters in `queue_mongo/storage.go` are named `timeout` rather than `ctx`.

## Consumers of this library

- **Emissary layers `tools/postcommit` on top** so tasks enqueued inside a database transaction are published only after commit ("the queue is the outbox"). Changes to `Publish` semantics ripple into that gate.
